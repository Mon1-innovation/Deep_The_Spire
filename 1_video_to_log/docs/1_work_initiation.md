# 第 1 步：工作启动结论与实现边界

> 日期：2026-09-15  
> 对应指示：human_guidelines/1_work_initiation.md  
> 状态：方向已收紧，可进入代码设计；少数产品决策待人工确认

## 1. 工作目标

将《杀戮尖塔 2》（STS2）高水平主播的完整录像转换为可追溯、可校验的事件流 JSONL，供后续“战斗日志 → LLM 数据集”阶段使用。首版覆盖整局：地图、战斗、事件、商店、篝火、宝箱、奖励、卡组与遗物查看，并保留音频转写及其与事件的时间对齐信息。

视频是唯一生产数据源；模组仅用于制作同步真值校验集，不能作为主播录像的运行时依赖。

## 2. 查证后的技术结论

### 2.1 关键帧与切分

没有发现适合本任务的现成“STS2 视频 → 日志”端到端项目。PySceneDetect、ffmpeg scene filter 等通用场景切分器可作为工程工具，但不适合作为主切分器：STS2 大部分时间是固定 UI，镜头几乎不切换，整帧变化不足以表达出牌、意图、能量和手牌变化。

首选方案是游戏语义驱动的两级切分：

1. 页面级粗切分：低分辨率、低频采样，分类为地图、战斗、商店、事件、篝火、奖励等。
2. 页面内细切分：在能量、手牌、HP、格挡、敌人意图、抽弃牌计数等 ROI 上做帧差分、pHash/SSIM 去重；取“变化结束后的首个稳定帧”作为状态边界。

现成项目的具体用途如下：

- PySceneDetect：页面切分和异常片段兜底。
- ffmpeg：抽帧、转码和无依赖 fallback。
- Video_Page_Extractor：稳定帧的 pHash + SSIM 去重参考。
- video2dataset：批量视频切段和帧数据工程胶水。
- OmniParser v2 / VLM-AutoYOLO：手牌、按钮和图标的定位/半自动标注参考，不承担事实重建。

因此，M2 的核心应是本地 CPU 的页面状态机、ROI 检测和稳定帧选择器；通用关键帧项目只作为组件，不再继续寻找“万能抽帧项目”。

### 2.2 画面转文字与实体识别

卡牌、遗物、药水、怪物和事件属于有限闭集，不能把 OCR 结果直接当事实。采用“卡面/图标缩略图检索 → 稳定 ID → 元数据表查询”的方式；只有无法匹配时才调用 VLM 或 OCR 作为歧义解析器。

元数据主源选用 ptrlrd/spire-codex，入库时必须带 STS2 patch 版本，以处理 Early Access 期间的数值和 UI 变化。必要的数字字段（HP、能量、格挡、层数）使用 ROI 识别，输出经过本地类型、枚举和 ID 存在性校验。

### 2.3 VLM、音频与事实来源

VLM 定位为观测器，不是事实来源。云端 API 只处理规则无法确定的局部问题：ROI 小问题、低置信升级和低频整屏文本界面。采用网格拼帧、ROI 裁剪、级联模型、幂等缓存、JSON Schema 结构化输出和 Batch API；目标为单局不超过约 500 次调用，并记录模型、prompt、版本、token 和费用。

事实由元数据、相邻观测、状态机和不变式决定。需要校验能量守恒、抽/弃/手牌数、HP/格挡变化范围、回合单调性和结算顺序；失败时标记为 uncertain，不能静默写入确定事实。

音频采用 Whisper/faster-whisper/WhisperX：首版做全文 ASR、词级时间戳，并将 utterance 对齐到决策事件的 ±2 秒窗口。是否“这句话解释了该决策的因果理由”暂不在本前置任务中判定，避免未经标注的语义归属污染训练数据。

## 3. 确定的首版需求

- 游戏：STS2。
- 范围：整局单人录像；多人合作暂不纳入首版。
- 输入：可访问的视频文件及可选音频；需记录 FPS、分辨率、来源和 UI 语言。
- 输出：事件流 JSONL，包含 run_id、patch、视频 provenance、事件时间戳、实体 ID、观测字段、评论音频时间戳和置信度。
- 置信度：至少分为 verified、inferred、uncertain。
- 可追溯性：每个事件保留触发帧时间戳、抽取器/模型版本和校验结果。
- 可恢复性：按视频段和单局断点续跑；单帧或单次 API 失败不得使整局作废。
- 质量闸门：抽样人工复核，并用日志重放检查 HP、能量和牌堆是否可复现。

## 4. 实现顺序与出口标准

| 里程碑 | 实现内容 | 出口标准 |
|---|---|---|
| M0 | spire-codex 元数据、patch 字段、schema v1、视频预处理接口 | 可按 ID/patch 查询；schema 冻结 |
| M1 | 模组真值录制工具与配对数据格式 | 20–50 局同步录像+真值日志 |
| M2 | 页面状态机、ROI 稳定帧检测、去重 | 页面/边界评测可重复；零 API 运行 |
| M3 | ROI/VLM 抽取、缓存、结构化校验、事件重建 | 单局 API ≤ 500；字段级指标可计算 |
| M4 | ASR 与事件时间对齐 | commentary 带词/句时间戳 |
| M5 | JSONL 导出、置信度分层、重放质检 | 合格样本可供下一阶段消费 |

建议首个可运行切片只覆盖一段战斗：combat_start → turn_start → card_played → enemy_turn → combat_end，先在真值集上验证状态边界和不变式，再扩展整局页面。

## 5. 待人工确认的未决项

以下事项会影响实现参数或数据合同，应在开始 M0/M1 前确认：

1. 可接受精度阈值：M1 建成后先测基线，再确定页面分类、实体识别、事件时间定位和字段准确率阈值。
2. 首批视频规范：最低分辨率/FPS、是否允许画中画、弹幕、剪辑加速、UI mod、混合语言；不合格片段的处理规则。
3. 云端 VLM 供应商与预算上限：决定批处理接口、图像 token 计费和可用 JSON Schema 能力。
4. 元数据语言与 patch 策略：首版是否只支持一种 UI 语言；patch 缺失或无法确定时是否允许输出低置信记录。
5. 真值模组与录制环境：采用哪个 STS2 日志模组、录制分辨率/FPS，以及真值时间戳的同步方法。
6. 日志 schema v1 的必填字段：尤其是地图选择、商店购买、事件选项和决策理由字段是否全部作为首版必填。

## 6. 结论

第 1 步已完成：工作方向收紧为“STS2 整局录像 → 语义事件切分 → ROI/检索优先的结构化观测 → 状态机与不变式重建 → 带 provenance 的 JSONL”。现有调研已足以进入 M0 的代码与数据合同设计；完成上节人工确认后即可锁定参数并开始实现。
